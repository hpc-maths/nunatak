# Caractérisation machine : plafonds mesurés par microbenchmarks embarqués, profil voyageant avec le Run

## Contexte et décision

Le roofline n'a de sens que si son plafond est atteignable en pratique. Un pic calculé théoriquement (`cœurs x fréquence x largeur SIMD x 2`) est systématiquement inatteignable - throttling AVX-512, turbo variable, limites cgroup - et un Hotspot à 60 % du vrai plafond apparaîtrait à 35 % du plafond théorique : la classification memory-bound / core-bound bascule sur cette erreur. Les plafonds d'une **Machine** sont donc **mesurés empiriquement sur la cible**, comme le font ERT, likwid-bench, Intel Advisor et rocprofiler-compute (ticket 03) ; le calcul théorique n'intervient qu'en repli, et le plafond est alors de Qualité « estimé ».

La mesure est réalisée par un **noyau de microbenchmark maison embarqué** (triad type STREAM pour les bandes passantes, chaînes de FMA en intrinsics par ISA pour les pics FLOP/s), livré en **wheels précompilées avec dispatch d'ISA à l'exécution**, avec recompilation locale en échappatoire quand l'ISA détectée n'est couverte par aucune variante embarquée. `likwid-bench` est orchestré en **raffinement optionnel** quand LIKWID est présent, pour affiner les plafonds hiérarchiques L1/L2/L3. Côté GPU, les kernels de calibration sont embarqués en **PTX** compilé par le driver à l'exécution pour NVIDIA (aucun toolkit requis, toute génération couverte) et en objets code pour les cibles `gfx` courantes pour AMD. Une seule exception à ce modèle de livraison : la **sonde réseau**, qui ne peut pas être précompilée et doit être construite avec le `mpicc` du site (voir Conséquences).

Le résultat est un **profil Machine** mis en cache dans `$XDG_CACHE_HOME/profiler/machines/`, dont la clé est l'empreinte canonique du matériel **combinée à la forme de l'allocation** (cœurs réellement visibles, masque d'affinité, limites cgroup) : un profil est réutilisé sur tous les nœuds identiques d'un cluster, mais un job qui reçoit 8 cœurs d'un nœud à 128 ne recycle pas les plafonds du nœud entier. Le manifeste du Run **embarque un instantané complet** de ce profil, si bien que le Placement roofline reste recalculable sur une autre machine ou des années plus tard, et que le cache n'est plus qu'une optimisation.

## Options considérées

- **Plafonds théoriques en principal** (cpuid, `nvidia-smi`, specs constructeur) : aucun coût à l'exécution, mais roofline biaisé par défaut, donc diagnostic biaisé par défaut.
- **Base de specs constructeur par modèle** : couverture immédiate du matériel courant, écartée pour sa maintenance sans fin (des milliers d'entrées, périmées à chaque génération) et son silence sur le matériel non répertorié.
- **`likwid-bench` comme chemin nominal** : meilleure couverture de microarchitectures, écartée parce que le chemin nominal dépendrait d'un paquet GPL externe absent de macOS et rarement installé.
- **Vendorisation d'ERT / STREAM** : code éprouvé et cité, mais ERT tire un driver Python et MPI, et le pic FLOP en C portable reste à la merci des choix du compilateur (émission de FMA, déroulage).
- **Cache site partagé, pré-rempli par l'administrateur du centre** : mutualise la calibration entre utilisateurs, écarté pour la v1 au profit d'un seul mécanisme de cache à spécifier, tester et déboguer.
- **Courbe de scaling complète** (plafonds à 1, 2, 4, 8... cœurs) : le plus rigoureux pour détecter la saturation mémoire, écarté pour son coût en temps de calibration.

## Conséquences

- La calibration se déclenche **automatiquement au premier Run sur une Machine inconnue**, avant le lancement de l'application : c'est le seul moment où l'utilisateur détient réellement le nœud de calcul, en exclusif. `profiler machine calibrate` permet de la provoquer, `--no-calibrate` de l'éviter au prix de plafonds « estimé ».
- Le **budget est borné à 60 s par défaut** et les plafonds sont mesurés **par ordre de priorité** : bande passante DRAM et pic FLOP double précision d'abord (sans eux il n'y a pas de roofline), puis simple précision, puis les niveaux de cache, puis le GPU. Un profil partiel reste exploitable, les plafonds non atteints restant « estimé ».
- Un plafond est le **maximum des répétitions**, jamais leur moyenne : c'est une borne supérieure. Les indices de pollution (charge externe, allocation non exclusive, dispersion entre répétitions, écart anormal au théorique) **rétrogradent le plafond en « estimé »** avec une raison textuelle, sans introduire de quatrième niveau de Qualité - le vocabulaire de l'ADR 0001 reste intact.
- Les plafonds sont mesurés **au périmètre de l'allocation**, plus **un point mono-thread** pour le diagnostic de scalabilité. Le Placement roofline **agrège les Mesures de tous les Loci de l'allocation** avant de comparer : même périmètre des deux côtés, sinon on compare la performance d'un rang au plafond d'un nœud.
- Le repli théorique s'appuie sur une **table par microarchitecture** (FLOP/cycle par précision, largeur SIMD, unités FMA - quelques dizaines d'entrées qui évoluent lentement) croisée avec ce que le système expose à l'exécution. **Microarchitecture inconnue : plafond « indisponible »**, jamais d'extrapolation.
- Le plafond **réseau** est mesuré par une sonde ping-pong lancée avec le lanceur MPI de l'utilisateur, avant l'application, quand le Run couvre plus d'un nœud ; sinon il est estimé depuis l'interconnect détecté.
- **La sonde réseau est le seul composant qui échappe à la livraison précompilée.** Elle doit être liée à l'implémentation MPI du site - une sonde construite contre une autre MPI ne se lancerait pas, ou pire, mesurerait un chemin de communication différent de celui de l'application. Elle est donc **compilée localement avec le `mpicc` du site**, à la première calibration réseau, et le binaire obtenu est mis en cache aux côtés du profil Machine. Le compilateur MPI est découvert à partir du lanceur observé dans la ligne de commande de l'utilisateur (`mpirun`, `srun`, `mpiexec`), afin de construire contre la même pile que l'application profilée et non contre une MPI arbitraire du `PATH`. Quand aucun `mpicc` utilisable n'est trouvé, ou quand la compilation échoue, le plafond réseau retombe sur l'estimation depuis l'interconnect détecté et le motif est consigné - jamais d'échec bloquant du Run. Le binaire de sonde en cache est invalidé comme le profil lui-même, plus un critère supplémentaire : un changement de pile MPI détectée (implémentation et version).
- Un profil en cache est invalidé par un **changement de version du noyau de microbenchmark** (des kernels différents rendent les plafonds incomparables). Gouverneur de fréquence et turbo sont enregistrés en métadonnée : s'ils ont changé, le rapport avertit, mais ne recalibre pas de lui-même. Pas de péremption dans le temps ; `profiler machine calibrate --force` reprend la main.
- **macOS n'est pas un mode dégradé pour la calibration** : le noyau maison y mesure de vrais plafonds en NEON. La dégradation macOS établie au ticket 02 porte sur le numérateur du roofline (pas de compteur FLOPs), pas sur son dénominateur.
- La librairie **cesse d'être un paquet Python pur** : elle distribue des wheels binaires par plateforme, du PTX et des objets code `gfx`. Conséquence directe pour le ticket 13 (packaging) et pour la matrice de build en CI.
